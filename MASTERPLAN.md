### Acceptance criteria and validation tasks

Do not pull P2/P3 work into implementation until P0 is stable and P1 scope is explicitly estimated. Every implementation phase must update README and run `npm test` + `npm run build`; browser/device claims need their own observed outputs.

- **F01 — motivation:** establish moment/session/long-term/meta goals in a one-page loop spec; every reward points to a visible next goal. Validate with at least five consented playtesters: at least 4/5 can explain why they would retry and what unlocks next. This is proposed research, not current data.
- **F02 — fairness:** one activity has explicit start, progress, success, failure, abort, score, medal and restart rules; scoring is deterministic from run inputs; no finish action grants a medal without satisfying the declared objective. Unit-test all threshold boundaries, cancellation, invalid score and repeated events; playtest assist/no-assist and seeded edge cases. No impossible layouts/requirements.
- **F03 — variety:** first slice has a documented seed and content table; same seed reproduces placements/outcomes; different seeds vary only within validated bounds. Add dynamic traffic/weather only with deterministic tests, readability checks and a replayable seed. Validate at least two materially different runs and one PB/replay flow.
- **F04 — authenticity/safety:** add a source/permission record for every real-world reference; use fictional brands/route names unless licensed; do a Bengali/Bangladesh cultural review before release. Frame driving as stylized closed-course fiction; no real-person/brand implication or harmful caricature. Review text, landmarks, vehicles and audio with local reviewers (not yet arranged).
- **F05 — economy:** P1-A now rejects unknown IDs and invalid/non-positive currency grants, derives upgrade/unlock/contract costs from the shared catalog, caps progress/levels, and makes claims idempotent. Existing smoke cases cover these rules; add generated/fuzzed malformed-value cases and publish a source/sink + upgrade-curve table before balancing. No pay-to-win, paid randomness, manipulative daily timers or streak loss.
- **F06 — feel/audio:** document input→steer/brake→camera/collision feedback; add deterministic collision/recovery tests and tune through recorded playtests; effects have independent master/music/SFX/voice sliders and mute. Validate no reward loop encourages real-road risk; test reduced-motion behavior. Do not add expensive physics or post-processing before device profiles.
- **F07 — first session:** from ready screen, player can drive within 10 seconds; one clear objective/control prompt; tutorial skippable; pause/settings reachable; finish/fail has quick retry (≤2 deliberate actions), and cancel never yields score/reward. Browser test on initial load and returning save; verify no console errors.
- **F08 — accessibility/input/localization:** release all input on blur, visibility loss and pointer cancellation; keyboard + touch work; gamepad/remapping planned; touch targets at least 48 CSS px (confirm physical size on device); permit zoom; support scalable HUD, non-color-only cues, captions, reduced motion and Bangla/English toggle with tested glyph fallback. - **F09 — data/performance:** P1-A defines schema v7, migrates v6, validates known fields and recovers malformed/denied storage to defaults; smoke fixtures cover missing fields, future versions and malformed values. Add oversized-storage simulation. Measure startup chunks, P50/P95 frame time, memory and draw calls on named devices before claiming budgets; preserve ESM and preallocated scratch math in hot loops. Compress/lazy-load only when assets warrant it; gate debug globals/cheats to development builds.
- **F10 — QA/CI:** add CI for `npm ci`, tests and build; browser smoke covers boot, controls, mode result/cancel and save; add bug report template with build/device/repro/expected/actual/log fields. Matrix: desktop Chromium, mobile viewport emulation, Android WebView on low/mid-tier devices; emulation is not a device pass. Run release artifact install/suspend/resume smoke before release.
- **F11 — tooling:** provide dev-only overlay for state/seed/quality/input and clearly marked cheats; validate content/schema and produce a balance summary in a Node tool; test that debug endpoints/cheats are absent in production build.
- **F12 — retention:** first add deterministic offline daily challenge, achievements/local bests and share card only if the core activity earns replay; provide opt-in playtest feedback without identifiers. Global leaderboard/multiplayer stays P3 pending threat model, anti-cheat, moderation and privacy approval.
- **F13 — privacy:** keep profile, PB and debug metrics local by default; no PII and no third-party tracking. Inventory browser/network requests and Android permissions; publish clear privacy policy before public web distribution. Analytics, if later justified, is opt-in, privacy-reviewed and data-minimized. Test offline play and no unexpected network request.
- **F14 — legal/security:** create credits and license/SBOM/asset-source ledger for code, packages, fonts, audio and art; confirm icon/splash sources. Add production CSP compatible with Three.js/WASM, avoid unsafe inline script where feasible, scan for secrets, review Android backup scope and INTERNET use. Require legal/owner review before store release; this is a checklist, not legal advice.
- **F15 — scope:** only one vertical slice and supporting reliability work until P1 gates are green. No full rewrite, backend by default, real-time multiplayer by default, gameplay ads, paid advantages, gambling mechanics, manipulative retention, copied trademarks/assets, or unnecessary dependencies. Review scope changes against all 15 lenses and update plan before code.
- **P0-01 — closed:** `npm test` asserts mismatched mode finish does not close a run, cancel is idempotent, emits no result, and does not mutate a medal. Re-run native back integration on Android when the SDK/device is available.

In a small consented playtest, target ≥4/5 players identifying the goal within 10 seconds and completing/retrying without facilitator help; this is a proposed metric, not current evidence.

## 4B. User-requested on-foot and real-time encounter expansion (design backlog)

**Vision, not implemented:** the user wants the main character to leave a vehicle, move on foot, enter another vehicle and engage NPCs in real-time arguments and fights (punches, kicks, slaps and sticks), inspired by the breadth and immediacy of GTA V. This is a major scope change, not a claim of GTA V feature parity. Build original locations, characters, writing, animations and assets; do not copy GTA's map, missions, trademarks or proprietary material. The current prototype has one driving state, decorative static NPCs and fixed traffic; it has no player avatar, on-foot controller, vehicle-entry ownership system or real-time combat. Existing Delivery/Rescue/Relay playthrough, P1 input/accessibility and release gates remain prerequisites for P2/P3 stage expansion; this request records the longer-term direction rather than closing those gates.

**Proposed order, subject to playtests and scope:**
1. **P1 foundation (in progress):** traffic/cow collider positions follow their visuals and an initial vehicle translation sweep stops at obstacles, with source and limited browser checks. A manual clear-position recovery cancels the current run, and proposed turn orientations are checked for overlap at movement endpoints; continuous rotational collision and impact handling remain incomplete. Complete existing playthrough/input/release gates and establish named-device baseline against the original ≤900k polygon / ≤220 MB limits, without assuming those limits are met.
2. **On-foot vertical slice:** in a small safe area, stop a vehicle and exit at a clear, collision-tested location; walk using keyboard and touch, approach one marked parked vehicle and enter it. A shared state machine owns control/camera/colliders and prevents moving-vehicle exits, entry from too far away, overlapping actors, duplicate input and loss of the active vehicle. Abort/reset, backgrounding and a blocked exit must leave a recoverable state. Start with temporary procedural art; no claim of a finished open world.
3. **NPC interaction:** one responsive fictional NPC with proximity prompts, readable dialogue and a real-time escalating argument; clear states and transitions, subtitles and dismissal. Distinguish NPCs from decorative bystanders and handle NPC/player separation and reset.
4. **Real-time fight slice:** a bounded encounter with an NPC opponent, player and NPC movement, punch, kick, slap, block/dodge and a stick action; hit detection tied to animation timing, distance and line of sight, readable tells, health and recovery, defeat/win/reset, abort and no reward duplication. NPC reactions and attacks run in real time; balance, visual intensity, weapons and whether bystanders can be targeted are open design choices for the user and review, not silently fixed here. Avoid stun locks and unavoidable attacks; test assist paths and reduced-motion/caption cues.
5. **Expansion only after validation:** multiple vehicles/NPCs, varied behaviours, encounter locations and persistent consequences; streaming, vehicle ownership/acquisition rules and save-schema migration designed only when needed. ## 6. Metrics and validation plan (targets are proposed, not observed)

5. **Performance:** build chunks (raw/gzip), startup to playable, P50/P95 frame time, draw calls, JS/GPU memory, thermal/battery observation on named devices (at least one low/mid Android WebView, one Adreno and one Mali if available). Proposed targets: 60 Hz frame budget 16.7 ms for capable tier and a stable 30 Hz fallback 33.3 ms; do not set ship claims until measured. 7. **Reliability/privacy:** CI test/build pass; browser boot/mode/save smoke; save migration/corruption recovery; zero unexpected outbound requests and zero PII in local metrics. Native plugin lifecycle and release install checked on real hardware.
8. **Scope:** every new feature has owner, acceptance test, effort estimate, dependency and all-15-lens review. P2/P3 remains backlog while P1 fails.
